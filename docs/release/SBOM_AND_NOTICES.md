# SBOM, Dependency Locks, and Third-Party Notices

**Status:** Implemented for local and CI packaging; not yet exercised with a
production-signed public release
**Applies to:** Ember `0.1.x` release candidates
**Last updated:** 2026-11-26

This document describes the supply-chain evidence Ember produces for a release:

1. committed Gradle dependency locks;
2. committed Gradle SHA-256 verification metadata;
3. a reproducible CycloneDX SBOM;
4. a generated third-party notice bundle.

It also records what those controls do **not** prove.

## 1. Gradle dependency locking

`build.gradle.kts` enables `dependencyLocking { lockAllConfigurations() }` for
every project. `gradle/verification-metadata.xml` and one `gradle.lockfile` per
project are committed, including `settings-gradle.lockfile` for dependency
resolution management.

A build now fails if a resolved module is absent from the lock state. To change a
dependency:

1. change `gradle/libs.versions.toml` or a build file;
2. run `.\scripts\update-dependency-locks.ps1`;
3. review the lockfile and verification-metadata diff;
4. run `.\scripts\build.ps1 -WithDependencyScan`;
5. commit the source change and all generated lock files together.

Do not hand-edit lockfiles or verification metadata. Do not run `--write-locks`
in CI.

## 2. Verification metadata

`gradle/verification-metadata.xml` records a SHA-256 checksum for every resolved
Maven artifact and Gradle plugin. `verify-metadata` is enabled and
`verify-signatures` is disabled because not every upstream artifact is signed and
the release pipeline does not yet maintain a trusted-key set. Checksums are the
control; signatures are a future improvement.

The metadata was generated by resolving the CI task set plus the Android release
variants and the Windows distributable. It was initially generated on Windows;
CI then resolved additional Linux-only metadata artifacts (Gradle Module
Metadata BOMs used by detekt and the Linux `aapt2` JAR). Those checksums were
downloaded from Maven Central and Google Maven, reviewed as a diff, and added by
hand. CI now exercises the metadata on both Windows and Linux for the CI task
set. If a runner resolves an artifact that is absent from the metadata, the build
fails closed; add the artifact by regenerating on that platform and review the
diff. That failure is intentional.

## 3. CycloneDX SBOM

`scripts/generate_sbom.py` writes CycloneDX 1.5 JSON. It derives components from:

- `Cargo.lock` through `cargo metadata --locked` (Cargo purls);
- `gradle/verification-metadata.xml` (Maven purls).

Workspace crates are represented by the Ember application component. The SBOM
contains no timestamp or random serial number, so the same lock data produces
byte-identical JSON. It records protocol v1, identify `0.1.0-stage-12`, storage
schema 11, and the component counts as properties.

The SBOM describes the **build graph**, including build and test dependencies.
It is deliberately larger than the runtime closure because the lock data does not
label scopes reliably. Known test-only Maven components are marked
`scope: excluded`.

Validate it with:

```powershell
python .\scripts\generate_sbom.py --version 0.1.0 --sbom .\dist\sbom\ember.cdx.json
```

The script rejects duplicate `bom-ref` values, missing required fields, invalid
purls, and an implausibly small component set.

## 4. Third-party notice bundle

The same script can build a notice bundle:

```powershell
python .\scripts\generate_sbom.py --version 0.1.0 `
  --sbom .\dist\0.1.0\Ember-0.1.0-sbom.cdx.json `
  --notices-dir .\dist\0.1.0\notices
```

The bundle contains:

- `THIRD_PARTY_NOTICES.md`: a generated summary of Rust and Maven components;
- `licenses/`: unique licence and notice texts, stored once by SHA-256;
- `license-files.json`: a machine-readable component-to-text mapping;
- `sbom.cdx.json`: a copy of the SBOM.

Licence files are read from the local Cargo registry and Gradle cache. AndroidX
AAR archives store notices under `META-INF/<group>/<name>/`, and the generator
reads both the AAR root and `classes.jar`. The JDK `legal/` tree is included when
`JAVA_HOME` is set.

The committed [THIRD_PARTY_NOTICES.md](../../THIRD_PARTY_NOTICES.md) is the
stable summary packaged inside the Windows application. The generated bundle is
shipped next to the artifacts and its digests are recorded in
`release-manifest.json`.

## 5. Release artifacts

`scripts/package-release.ps1` produces, in addition to the APK, AAB, MSI, and
portable ZIP:

| File | Kind |
|---|---|
| `Ember-<version>-sbom.cdx.json` | CycloneDX 1.5 SBOM |
| `Ember-<version>-third-party-notices.zip` | Notice summary, licence texts, mapping, and SBOM copy |

Both are hashed in `SHA256SUMS` and described in `release-manifest.json`. They
are not signed individually; the manifest and checksums bind them to the signed
artifact set.

## 6. Current local evidence

On 2026-11-27 an unsigned dry run produced:

- a CycloneDX 1.5 SBOM with 1,130 components (399 Cargo, 731 Maven);
- 333 unique licence texts in the notice bundle;
- 46 Cargo and 503 Maven components with no local licence file, still listed
  with their declared licence or as `NOASSERTION`;
- `verify-release.ps1` passing on the SBOM and notice bundle.

The dry run is local and unsigned. It is not a published release.

## 7. What is still not proven

- Gradle verification metadata has been exercised by CI on Windows and Linux for
  the CI task set. The Linux Android release variants and the release workflow
  have not been run with the committed metadata.
- The SBOM is not attested with an in-toto or SLSA provenance statement.
- The notice bundle is generated best-effort. Some build-only archives contain
  no licence file; the generator reports the count, and a public release still
  needs a reviewed bundle with no unexplained component.
- Locking and checksums make builds **verifiable in inputs**. They do not make
  jpackage or native output bit-identical.
- No release using these controls has been published.
